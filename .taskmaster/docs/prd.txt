# PRD - Smart Hospitals
## 1. Contexto
Este projeto é uma prova de conceito de uma aplicação hospitalar inteligente. Esta POC está sendo
desenvolvida no estado de São Paulo - Brasil. O país vive uma onda de digitalização e smartização.
O Sistema Único de Saúde-SUS tem demonstrado interesse na construção de hospitais inteligentes.
Esta POC é o ponta-pé inicial para uma série de demonstrações para a validação de viabilidade e posterior
implementação em ambientes hospitalares reais. Nesta primeira fase do projeto, serão utilizados dados do
InfoDengue. Um dashboard será construído no Streamlit para demonstrar os dados da base. Este dashboard
também contará com um MCP server para ser consumido pelos agentes hospitalares de IA. Através deste MCP
os agentes atualizarão seus respectivos contextos, para assim poderem auxiliar os humanos nas mais diversas tarefas
associadas ao contexto hospitalar.

## 2. Objetivo
O esperado nesta primeira fase é um dashboard claro e informativo, com um MCP server capaz de fornecer
um panorama geral sobre a situação epidemiológica da dengue para os agentes de IA.

## 3. Usuário-alvo
Tratando-se de uma PoC o usuário alvo, a princípio, é fictício. É baseado em um tomador de decisões de alta hierarquia
dentro de um hospital.
Exemplo de caso de uso:
Tomador de decisões: Estou com poucas doses de um medicamento X. Qual a tendência de casos de dengue para as próximas semanas?
Agente de IA hospitalar:
Consulta ao MCP server -> Resposta do MCP: Rt = 1,4; probabilidade de crescimento (p_rt1) = 95%;
nível de alerta laranja; +35% de casos estimados em relação à semana anterior -> Resposta ao usuário:

"A tendência é de alta nos casos de dengue. É sugerido antecipar as compras."

Observação: nesta fase o MCP informa a situação atual e indicadores de tendência; ele não produz previsão numérica
de casos futuros (ver Fora de escopo).

## 4. Escopo (nesta versão)
- Script de extração que baixa da API do InfoDengue os dados de dengue do município de São Paulo
  (capital, código IBGE 3550308), da semana epidemiológica 1 de 2010 até a mais recente, e salva um
  snapshot CSV versionado no repositório.
- Análise dos dados via Jupyter notebook, com sugestões de visualizações para o painel.
- [Aprovação humana 1] Documento `docs/visualizacoes.md`, preenchido pelo responsável humano, com as
  visualizações escolhidas para o dashboard. A implementação do dashboard só começa após esse documento.
- Protótipo do dashboard executado localmente.
- [Aprovação humana 2] Validação do design do protótipo pelo responsável humano. A publicação só acontece
  após essa aprovação.
- Publicação do dashboard, com as visualizações aprovadas, no Streamlit Community Cloud.
- MCP server da aplicação, executado localmente via stdio (consumível por clientes MCP como Claude Desktop/Claude Code)

## 5. Fora de escopo (explicitamente)
- Não será criado um agente consumidor agora.
- Modelo de previsão de casos futuros (previsto para uma fase seguinte).
- Publicação do MCP server na internet (transporte HTTP); nesta fase ele roda apenas localmente via stdio.
- Outros municípios além da capital paulista e outras doenças (chikungunya, zika).
- Atualização automática dos dados; o snapshot é atualizado manualmente, rodando o script de extração.

## 6. Requisitos funcionais
- RF01: Dashboard publicado
- RF02: Disponibilização via MCP da situação atual e de indicadores de tendência da dengue, a partir dos dados
  do InfoDengue: casos notificados, casos estimados (nowcast, com intervalo), Rt, probabilidade de Rt > 1 (p_rt1),
  variação semanal de casos e nível de alerta.
  O MCP server expõe as seguintes tools (somente leitura, todas informando a data de referência do snapshot):
  - situacao_atual(): data de referência, casos notificados, casos_est (mín./máx.), incidência por 100 mil hab.,
    nível de alerta, Rt, p_rt1 e variação em relação à semana anterior.
  - tendencia(semanas=4): indicadores das últimas N semanas e um resumo da tendência (alta, estável ou queda),
    derivado de Rt, p_rt1 e variação semanal.
  - serie_historica(inicio, fim): série semanal no intervalo pedido (semanas epidemiológicas ou datas).
  - comparativo_sazonal(semana=None): semana atual (ou a informada) comparada com a mesma semana dos anos
    anteriores (média, mínimo e máximo).

## 7. Requisitos não funcionais
- RNF01: Segurança e privacidade
  - Os dados do InfoDengue são públicos e agregados por semana, sem dados pessoais; o projeto não coleta
    nem armazena dados de pacientes.
  - O MCP é somente leitura e valida os parâmetros das tools (tipos e intervalos), retornando erro claro
    para entradas inválidas.
  - Nenhum segredo é versionado no repositório.
- RNF02: Observabilidade mínima
  - O MCP server registra cada chamada de tool: nome, parâmetros, duração e sucesso/erro.
  - Os logs vão para stderr; o stdout é reservado ao protocolo MCP (transporte stdio) e não pode receber
    nenhuma outra saída.
  - O script de extração registra quantas semanas foram baixadas e o intervalo coberto.
- RNF03: Testabilidade
  - Testes com pytest, cobertura mínima de 80% no módulo de dados e no MCP server.
  - Os testes usam o snapshot versionado (ou uma amostra fixa dele) e não acessam a rede.
  - O dashboard tem um teste de fumaça com streamlit.testing.AppTest, verificando que o app carrega sem erro.
- RNF04: Performance
  - Cada tool do MCP responde em menos de 1 s localmente (dados em memória).
  - O dashboard carrega em menos de 5 s no Streamlit Community Cloud com o app ativo (o tempo de
    despertar após inatividade não é considerado).

## 8. Arquitetura inicial
Linguagem: Python 3.12. Gestor de pacotes e ambiente: uv (pyproject.toml + uv.lock).
Extração de dados: pandas lendo diretamente a API do InfoDengue (formato CSV).
Análise de dados (notebook Jupyter, dependência de desenvolvimento): pandas, numpy, seaborn, matplotlib.
Dashboard: Streamlit + Plotly (gráficos interativos), publicado no Streamlit Community Cloud.
MCP server: SDK oficial `mcp` para Python (FastMCP), transporte stdio, execução local.
Qualidade: pytest + pytest-cov (testes), ruff (lint e formatação), mypy (checagem de tipos), executados
também via pre-commit.

Dados: snapshot CSV versionado no repositório, gerado por um script de extração a partir da API do
InfoDengue (município de São Paulo, IBGE 3550308, dengue, desde 2010). Dashboard, MCP e testes leem
apenas o snapshot; nenhum deles depende da API em tempo de execução.

Dashboard e MCP server são processos independentes que compartilham um mesmo módulo de dados em Python
(leitura do snapshot, limpeza e cálculo dos indicadores). Assim os dois expõem os mesmos números.
"Situação atual" significa a semana epidemiológica mais recente presente no snapshot; o dashboard e as
respostas do MCP devem sempre informar essa data de referência.

    API InfoDengue -> script de extração -> snapshot CSV (versionado)
                                                 |
                                       módulo de dados (Python)
                                         |                  |
                     Dashboard Streamlit (Streamlit Cloud)  MCP server (FastMCP, stdio, local)

## 9. Critérios de aceite
- O sistema DEVE: ter o dashboard publicado no Streamlit Community Cloud, exibindo as visualizações
  aprovadas e a data de referência dos dados.
- Os testes DEVEM: mostrar que o dashboard publicado responde (HTTP 200) e que o MCP server, iniciado
  localmente via stdio, lista suas tools e responde a cada uma com dados válidos.
- A documentação (README) DEVE explicar como: atualizar o snapshot com o script de extração; rodar o
  dashboard localmente; rodar os testes; e conectar o MCP server a um cliente MCP (ex.: Claude Desktop).

## 10. Riscos e validações
Falhas de layout
Falhas de resposta do MCP
Dados desatualizados: o snapshot envelhece. Mitigação: data de referência sempre visível no dashboard e
presente nas respostas do MCP; script de extração documentado para atualização manual.
Semanas recentes incompletas: atraso de notificação faz as últimas semanas parecerem em queda.
Mitigação: usar casos_est (nowcast) com intervalo para as semanas recentes.

## 11. Premissas
- A API do InfoDengue é pública, não exige chave e possui dados de dengue do município de São Paulo
  desde 2010.
- O snapshot CSV fica abaixo do limite de 500 KB do hook check-added-large-files do pre-commit.
- O plano gratuito do Streamlit Community Cloud é suficiente para a PoC.

## 12. Métricas de sucesso
- Dashboard publicado e acessível por URL pública, com as visualizações aprovadas.
- As quatro tools do MCP respondendo corretamente a partir do snapshot.
- Testes passando com cobertura de pelo menos 80% no módulo de dados e no MCP server.
- Demonstração: um cliente MCP (ex.: Claude Desktop) conectado ao MCP server responde à pergunta do caso
  de uso (seção 3) usando os dados retornados pelas tools.
